# Deployment Plan: Weather Vector Search

The application has two supported targets:

- **Local development**: Docker Compose runs Flask and PostgreSQL/pgvector without
  Databricks credentials. Its API port is published only on localhost.
- **Course deployment**: Databricks Apps runs Flask and connects to Lakebase. Databricks
  workspace SSO and app permissions restrict access; anonymous/public access is not
  supported.

The same schema DDL is used for both databases. The implementation should save this SQL
as `sql/weather_schema.sql` and run it with the target database's owner/admin account.

## Shared Lakebase/PostgreSQL schema SQL

Run this in the target database after confirming that `pgvector` is available. The
`CREATE EXTENSION` statement may require a Lakebase database owner or administrator.

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE SCHEMA IF NOT EXISTS weather;

CREATE TABLE IF NOT EXISTS weather.weather_saved_locations (
    id UUID PRIMARY KEY,
    input_type TEXT NOT NULL
        CHECK (input_type IN ('city_state', 'coordinates')),
    input_value JSONB NOT NULL,
    display_location TEXT NOT NULL
        CHECK (length(trim(display_location)) > 0),
    latitude DOUBLE PRECISION
        CHECK (latitude IS NULL OR (latitude >= -90 AND latitude <= 90)),
    longitude DOUBLE PRECISION
        CHECK (longitude IS NULL OR (longitude >= -180 AND longitude <= 180)),
    grid_id TEXT,
    grid_x INTEGER,
    grid_y INTEGER,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CHECK ((latitude IS NULL) = (longitude IS NULL))
);

CREATE TABLE IF NOT EXISTS weather.weather_documents (
    id TEXT PRIMARY KEY,
    grid_id TEXT,
    grid_x INTEGER,
    grid_y INTEGER,
    source_type TEXT NOT NULL
        CHECK (source_type IN ('alert', 'forecast')),
    forecast_type TEXT,
    headline TEXT,
    narrative_text TEXT NOT NULL
        CHECK (length(trim(narrative_text)) > 0),
    narrative_hash TEXT NOT NULL,
    issued_at TIMESTAMPTZ,
    effective_at TIMESTAMPTZ,
    period_start TIMESTAMPTZ,
    period_end TIMESTAMPTZ,
    payload JSONB NOT NULL,
    synced_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    embedding_status TEXT NOT NULL DEFAULT 'pending'
        CHECK (embedding_status IN ('pending', 'current', 'stale')),
    CHECK (
        (
            source_type = 'alert'
            AND forecast_type IS NULL
            AND period_start IS NULL
            AND period_end IS NULL
            AND grid_id IS NULL
            AND grid_x IS NULL
            AND grid_y IS NULL
        )
        OR
        (
            source_type = 'forecast'
            AND forecast_type IS NOT NULL
            AND forecast_type IN ('daily', 'hourly')
            AND period_start IS NOT NULL
            AND period_end IS NOT NULL
            AND period_end > period_start
            AND grid_id IS NOT NULL
            AND grid_x IS NOT NULL
            AND grid_y IS NOT NULL
        )
    )
);

CREATE TABLE IF NOT EXISTS weather.weather_location_documents (
    saved_location_id UUID NOT NULL
        REFERENCES weather.weather_saved_locations(id) ON DELETE CASCADE,
    document_id TEXT NOT NULL
        REFERENCES weather.weather_documents(id) ON DELETE CASCADE,
    PRIMARY KEY (saved_location_id, document_id)
);

CREATE TABLE IF NOT EXISTS weather.weather_embeddings (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    document_id TEXT NOT NULL
        REFERENCES weather.weather_documents(id) ON DELETE CASCADE,
    chunk_index INTEGER NOT NULL CHECK (chunk_index >= 0),
    chunk_text TEXT NOT NULL CHECK (length(trim(chunk_text)) > 0),
    chunk_hash TEXT NOT NULL,
    embedding VECTOR(384) NOT NULL,
    model_name TEXT NOT NULL,
    model_revision TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT weather_embeddings_document_chunk_key
        UNIQUE (document_id, chunk_index)
);

CREATE INDEX IF NOT EXISTS weather_embeddings_document_id_idx
    ON weather.weather_embeddings (document_id);

CREATE INDEX IF NOT EXISTS weather_location_documents_document_id_idx
    ON weather.weather_location_documents (document_id);

CREATE INDEX IF NOT EXISTS weather_embeddings_embedding_hnsw_idx
    ON weather.weather_embeddings
    USING hnsw (embedding vector_cosine_ops);

CREATE INDEX IF NOT EXISTS weather_documents_embedding_status_idx
    ON weather.weather_documents (embedding_status);
```

`IF NOT EXISTS` makes this suitable for repeatable setup on a fresh/current schema; it
does not alter an already-existing table if a later implementation changes its
definition. Any future schema evolution must use a versioned migration rather than
relying on this bootstrap DDL to change existing columns.

Generate saved-location UUIDs in the application. When removing a location, use one
transaction to remove its associations and saved-location row, then delete weather
documents with no remaining location associations. The `weather_embeddings` foreign key
cascades deletion to chunks and vectors; documents still associated with other saved
locations remain searchable there.

### Upgrade an existing weather database

The original schema stored one `location` and coordinate set directly on each
`weather_documents` row and did not persist the frontend location list. Do not rely on
the bootstrap SQL above to transform such a database. Apply a versioned migration before
deploying the new application:

1. Create `weather_saved_locations` and `weather_location_documents`.
2. Backfill one saved location for each distinct legacy location/coordinate/grid tuple,
   preserving its display label and resolved NWS values.
3. Associate each existing weather document with the saved location represented by its
   legacy location fields. Keep existing documents and embedding rows; do not rebuild
   vectors solely because of this migration.
4. Verify every document has at least one location association before switching the app
   to the new search and deletion behavior.

The migration must run transactionally and be safe to resume or explicitly report a
failure without dropping existing weather data. It retains legacy document location
columns but makes them nullable, as well as the legacy grid columns, so new alert rows
can use the normalized shared-document schema. Existing source documents and embedding
rows remain intact.

### Lakebase app-role grants

First add the Lakebase database as an app resource so Databricks creates the app's
PostgreSQL role. Then run the following as a database owner, replacing
`APP_SERVICE_PRINCIPAL_ROLE` with the exact role name shown for the app. Quote the
identifier as shown because the role is a client ID and can contain punctuation.

```sql
GRANT CONNECT ON DATABASE "<DATABASE_NAME>" TO "APP_SERVICE_PRINCIPAL_ROLE";
GRANT USAGE ON SCHEMA weather TO "APP_SERVICE_PRINCIPAL_ROLE";
GRANT SELECT, INSERT, UPDATE, DELETE
    ON ALL TABLES IN SCHEMA weather TO "APP_SERVICE_PRINCIPAL_ROLE";
GRANT USAGE, SELECT
    ON ALL SEQUENCES IN SCHEMA weather TO "APP_SERVICE_PRINCIPAL_ROLE";

ALTER DEFAULT PRIVILEGES FOR ROLE "SCHEMA_OWNER_ROLE" IN SCHEMA weather
    GRANT SELECT, INSERT, UPDATE, DELETE
    ON TABLES TO "APP_SERVICE_PRINCIPAL_ROLE";
ALTER DEFAULT PRIVILEGES FOR ROLE "SCHEMA_OWNER_ROLE" IN SCHEMA weather
    GRANT USAGE, SELECT
    ON SEQUENCES TO "APP_SERVICE_PRINCIPAL_ROLE";
```

Replace `SCHEMA_OWNER_ROLE` with the role that creates future tables in `weather`.
The Lakebase resource grants the app database-level `CONNECT` and `CREATE` privileges;
the schema/table grants above allow the app to use objects created by the database
owner without granting it ownership of the entire schema.

For local Compose, the PostgreSQL initialization user can apply the schema script. The
local database is reachable only from the Compose network and its credentials are for
development only.

## Databricks deployment steps

1. **Check workspace prerequisites.** Confirm the Databricks workspace and region support
   Databricks Apps and Lakebase Autoscaling, and that the deployer can create/manage an
   app and has permission to add the selected Lakebase project as an app resource.
2. **Provision Lakebase.** Create or select a Lakebase Autoscaling project, branch, and
   database. Connect to the database as its owner/admin and run the shared schema SQL
   above. Verify `vector` is enabled and the HNSW index exists.
3. **Create the app and add the database resource.** Create a Databricks App from the
   Flask template or deploy this project as an app. Add the Lakebase project, branch,
   and database under App resources. Databricks creates a database role for the app's
   service principal and supplies `PGAPPNAME`, `PGDATABASE`, `PGHOST`, `PGPORT`,
   `PGSSLMODE`, and `PGUSER`.
4. **Grant database access.** Find the service-principal PostgreSQL role and apply the
   app-role grants above. Keep extension installation and schema ownership with the
   database owner/admin.
5. **Configure the app runtime.** Include a root `app.yaml` and deploy Flask through
   Gunicorn, binding to `0.0.0.0` and the platform-provided
   `DATABRICKS_APP_PORT`. Configure `LAKEBASE_ENDPOINT` using the endpoint path format
   `projects/<project-id>/branches/<branch-id>/endpoints/<endpoint-id>` required by the
   Databricks SDK's database-credential API. Use the injected app service-principal
   credentials and fetch a fresh OAuth database token when opening a Psycopg 2
   connection; tokens expire after one hour. Do not copy credentials or OAuth tokens
   into source files.
6. **Deploy and restrict access.** Deploy from the Databricks workspace UI or supported
   Databricks CLI. Grant `CAN USE` to the course cohort and `CAN MANAGE` only to
   maintainers. Databricks Apps requires workspace authentication and does not permit
   anonymous/public access; the Flask routes do not add a separate per-user auth layer.
7. **Demonstrate the live flow.** Open the app URL from its Databricks overview page,
   add one or more locations in the frontend, reload the page to confirm persistence,
   and synchronize them. Review the per-location outcome and whether the 20-request
   budget was exhausted. The server caps attempts at 20 per location per sync, including
   retries. Run the embedding batch process with the deployed app's database
   configuration, then enter a search query in the frontend and review its ranked
   matches, all associated saved locations, and source/freshness metadata. Remove a
   location and confirm only documents no longer associated with any saved location and
   their chunks are deleted. Confirm rows and the HNSW index in the Lakebase SQL editor.
   A first connection may take longer while Lakebase scales up.

## Local Compose demonstration

The local workflow is documented in [quickstart.md](quickstart.md). It starts the same
Flask application with a local PostgreSQL/pgvector service, applies the same schema SQL,
and does not require Databricks credentials. The app port must be bound to
`127.0.0.1`; do not publish the database service port on the host.
